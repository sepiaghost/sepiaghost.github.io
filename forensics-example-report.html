1. Executive summary

GenoVault is a fictional controlled-access genomic data repository. On 2026-08-22 its operators reported unusual download volumes on 21-22 August. Separately, the sequencing core flagged that the delivered files for subject S-0457 (tumour/normal exome) looked inconsistent with one another. The examiner was asked to review the delivered files and the repository access logs, plus the laboratory's Sample Tracker custody database. Subject codes are de-identified.

9 evidence items were hashed on intake, examined read-only, and re-hashed at close (all hashes unchanged). The examination produced 12 high, 17 medium and 1 low severity findings.

  • INC-1: probable unauthorised use of account res_03. Activity from 192.0.2.45 and 192.0.2.77: 38 failed logins preceded a successful login; 22.90 GB was downloaded across 5 controlled datasets (4 outside the account's approvals), and an API token was created.
  • Paired FASTQ S-0457_R1.fastq.gz / S-0457_R2.fastq.gz are not consistent: 2,000 vs 1,963 reads, 187 read names only in R1 and 150 only in R2.
  • Sample identity: tumour vs retained normal (control): concordance 98.0% over 3,000 shared sites, consistent with the same individual.
  • Sample identity: tumour vs delivered normal. Genotype concordance 44.5% over 3,000 shared sites does not support same-individual origin.
  • S-0457_normal_delivered.vcf shows 2 structural/consistency findings (VCF-ORDER, VCF-TIME).
  • BAM S-0457_N_delivered.bam shows 5 consistency findings (BM-FLOWCELL, BM-REHEADER, BM-RG-UNDECLARED, BM-SORT, BM-TIME).
  • BAM S-0457_N_delivered.bam cannot be reconciled with its FASTQ files: of 600 read names, 450 are in both mates, 0 only in R1, 150 only in R2 and 0 in neither.
  • Custody records sample_tracker_custody.db are not internally consistent: 3 findings (CU-HASH, CU-STATE, CU-TRIGGER) affecting S-0457-N.
  • 2 isolated log findings did not correlate to an incident and need context from the account owner before being treated as malicious.
Findings are observations with stated confidence, not conclusions about intent. See section 9 for what each result does and does not establish.

4. Methodology

  • Evidence is opened read-only; hashes are taken before and after analysis to demonstrate that nothing was altered.
  • Genomic files are checked for structure, internal consistency and plausibility, then compared with each other (R1 vs R2 read names; shared-site genotype concordance between VCF samples; BAM header, read groups and sort order, and whether a BAM's reads and sample name agree with the FASTQ and VCF files it belongs with).
  • Access logs are split into a baseline period (2026-08-01T02:00:23Z to 2026-08-15T02:00:23Z) and an analysis period. Per-account baselines (source addresses, client signatures, active hours, daily download volume) are compared with analysis-period activity using explainable rules (Appendix A).
  • Chain-of-custody databases (Sample Tracker) are opened read-only and immutable. The hash chain is recomputed with an independent implementation of the tracker's hash specification, and the inventory is compared with the last logged state of each sample.
  • Rule hits that share an account or source address within 24 hours are correlated into incidents (three or more distinct rules); everything else is reported as an isolated finding.
  • Each log finding lists the originating log row numbers so it can be checked against the raw evidence.

9. Conclusions

  • INC-1 / account res_03: the sequence of repeated failed logins, a success from an address and client never seen for this account, enumeration of datasets, retrieval of 22.90 GB including 4 datasets outside the account's approvals, and creation of an API token is consistent with unauthorised use of valid credentials. The logs do not identify the person responsible, and they do not show how the password was ultimately obtained beyond the repeated-guess pattern. That unapproved datasets could be downloaded at all indicates the approval list was not enforced by the repository.
  • FASTQ pair S-0457_R1.fastq.gz / S-0457_R2.fastq.gz: the two files do not describe the same set of read pairs. R2 additionally contains reads naming a second flowcell (H5ABCDRXY (150 reads)) alongside the main run (HXYZ123DSXX), so its read names do not come from a single sequencing run, and 4 record(s) have a quality string that does not match the sequence length. This is consistent with R2 having been edited after sequencing (records removed and replaced). Accidental causes such as a failed transfer, an interrupted copy or a faulty merge step are not excluded by file analysis alone; the sequencing core's original files and transfer logs are needed to decide between them.
  • Sample identity, tumour vs retained normal (control): 98.0% concordance over 3,000 sites is consistent with one individual (small differences are expected from somatic variation and technical noise).
  • Sample identity, tumour vs delivered normal: 44.5% concordance over 3,000 sites is far below what one individual produces. This supports a sample swap or mislabelling between the two files. It cannot say where in the workflow it happened or whether it was accidental.
  • S-0457_normal_delivered.vcf: Records are not in coordinate order; Header ##fileDate is later than the file's modification time. These are indicators of manual editing, merging or file handling after the variant caller produced the file; they should be checked against transfer logs and the LIMS record before drawing any conclusion about intent.
  • BAM S-0457_N_delivered.bam: Header says SO:coordinate but 77 record(s) are out of order; Reads belong to read groups the header does not declare; Read names come from a flowcell that no read group mentions; Header was rewritten after alignment; Read-group DT is later than the file's modification time. Taken together, a read group the header never declared, reads from a flowcell no read group mentions, records out of the declared sort order and a rewritten header describe an alignment file that was assembled or edited after the aligner finished. Each finding has an innocent explanation on its own (re-heading to fix a label is routine). The combination, and the match between the foreign reads and the reads found only in R2, is what makes them hard to explain as a normal workflow. The file cannot show who changed it or why.
  • BAM / FASTQ cross-check: 150 BAM read name(s) exist in R2 but not in R1 (examples: NB501234:12:H5ABCDRXY:2:1101:10061:1096, NB501234:12:H5ABCDRXY:2:1101:10156:1149, NB501234:12:H5ABCDRXY:2:1101:10237:1108). A read pair that aligned came from both mates, so this fits R2 and the BAM having been altered with material from the same other run. It does not identify which file was changed first.
  • BAM / VCF cross-check (S-0457_N_delivered.bam / S-0457_normal_delivered.vcf): the two files agree on sample name and reference contigs. This does not contradict the sample-identity result above: a matching label says nothing about whether the genotypes belong to the individual that was sequenced, which is what the concordance test examines.
  • Custody records sample_tracker_custody.db: the database shows 3 integrity finding(s) affecting S-0457-N. Entries whose content no longer matches their hash, and inventory values that differ from the last logged state with no log entry, mean the records were changed outside the tracker application's normal workflow. For entry 10, recomputing the hash with actor = 'tech_02' reproduces the stored hash, so that was probably the original value; the record now says 'tech_01'. This is consistent with direct edits to the database file. The records cannot show who made the edits, when, or why, and they should not be relied on to establish who handled the affected samples until reconciled against other records (freezer logs, sequencing-core receipts, badge or access records).
  • No integrity anomalies at medium level or above were detected in: S-0457_R1.fastq.gz, S-0457_normal_retained.vcf, S-0457_tumour.vcf. Absence of findings does not prove a file is authentic; it means these checks did not detect a problem.

10. Limitations and assumptions

  • This tool detects inconsistencies and anomalies; it cannot prove who made a change or why. Findings should be corroborated with transfer logs, LIMS records and original source files.
  • Filesystem timestamps change when files are copied or extracted, so timestamp findings are leads rather than proof.
  • Identity comparison assumes both VCFs report the same site set (panel/array-like, or callsets including 0/0). The 95% threshold is a heuristic; close relatives and low site counts can blur it.
  • Log baselines come from a short window. New addresses and off-hours work are common for legitimate reasons (travel, VPN, deadlines), which is why single-rule hits are triaged, not escalated.
  • A tracker hash chain proves consistency of entries with each other, not the truth of what was entered. A full rewrite of the chain would be detectable only against an externally stored head hash.
  • Logs are assumed complete and unaltered; the report cannot detect deleted or forged log entries. Log times are taken as UTC as written.
  • BAM checks cover the container, header, read groups, sort order and read names. They do not re-align reads, validate base qualities, or compare reads with VCF genotypes, so a BAM can pass them and still carry the wrong individual's reads.
  • FASTQ/VCF/BAM parsing is in pure Python and intended for small-to-medium files; large production files would need sampling or a compiled toolchain.
  • Detection thresholds are listed in Appendix A and can be tuned; a different threshold can change which items appear.

11. Recommendations

  • Disable the affected account and revoke all API tokens it issued; reset credentials and review any data shared onward.
  • Enforce multi-factor authentication and account lockout / rate limiting on the login endpoint.
  • Enforce dataset approvals server-side for every controlled-access request and alert on denied or unapproved attempts.
  • Alert on bulk downloads and on activity outside an account's usual hours or addresses; investigate token creation from new addresses.
  • Preserve and export repository logs to write-once storage so they can support later review.
  • Obtain the original FASTQ files from the sequencing core, compare hashes, and re-run delivery for the affected sample.
  • Obtain the original alignment from the sequencing core and compare hashes; if it cannot be reproduced, re-align from verified FASTQ rather than repairing the delivered BAM's header.
  • Re-verify sample identity against the retained reference material (e.g. with a fingerprinting panel) before any result from the affected sample is used.
  • Restrict write access to the custody database file, restore its append-only triggers, and compare the current file with backups to establish when it changed.
  • Reconcile the affected samples' movements against independent records (freezer logs, sequencing-core receipts) before trusting the tracker for those samples.
  • Record each day's head hash in a separate write-once location so any later rewrite of the chain is detectable.
  • Record a cryptographic hash for every genomic file at acquisition and re-verify at each hand-off.
